MMagika · architecture field notes

From one cat to twenty million people

Raw traffic is not what forces a big architecture. MMagika’s page stores nothing, so 20M users is only ~160 requests a second on average. What forces new parts is remembering things, slow work, many systems reacting to the same events, and serving the whole planet through outages. Each stage below adds exactly one of those.

20 million users, in requests

Monthly users20,000,000
Daily actives (assume 10%)2,000,000
Requests / day (3 pages + 4 API calls each)≈ 14M
Average load≈ 160 req/s
Peak hour (×3)≈ 500 req/s
Viral spike (×20)≈ 3,200 req/s
Page bytes / day (40 KB × 6M)≈ 240 GB
Illustrated scrolls (10% of 2M × 5 s)≈ 12 busy workers

Assumptions, not measurements. The local server log shows ~1 ms of work per API call. Change the inputs and the shape of the answer stays the same.

Render vs AWS in one breath

Render is a furnished flat. You describe your services in render.yaml, push to git, and it provides the wiring: HTTPS, load balancing, deploys, restarts, private networking, managed databases.

AWS is a builder’s yard. Every piece exists (and more), but you choose, connect, secure and pay for each one: network, balancer, certificates, scaling rules, pipelines.

Same architecture ideas on both. The difference is who assembles it, and how far you can go before you hit the platform’s edges.

Stage 1 of 6Today → ~50k users

One service

One Python process group behind HTTPS. This is exactly what the repo deploys right now.

Move here when: You want it online, and nothing else yet.

In junior terms

Web service
The computer that runs your Python and answers requests.
gunicorn 2 × 4
Runs 2 copies of the app with 4 threads each, so one slow visitor doesn’t block the other seven.
HTTPS / TLS
The padlock. It encrypts traffic and proves the site is really yours.
Health check
Something pings /healthz every few seconds. No answer means restart.
DNS (Route 53)
The phone book that turns mmagika.com into a server address.
Load balancer (ALB)
A receptionist who takes every visitor and walks them to a free server.
VPC & security groups
Your private fenced-off network in AWS, and the list of who may talk to whom.
IAM
Permission slips: which machine or person is allowed to do what.

What actually changes

The app is already built for this stage: config comes from environment variables, logs are one JSON line per request, /healthz answers probes, and deploys are just git push.

The one decision that pays off later: the server remembers nothing. No database, no logins, no sessions, so there’s nothing to scale, back up or lose, and any copy can answer anyone.

On Render you…

  • Connect the repo as a Blueprint (reads render.yaml)
  • Render generates SECRET_KEY
  • Done: HTTPS URL in about 2 minutes

On AWS you…

  • Create a VPC, public subnets, internet gateway
  • ALB, target group, ACM certificate, Route 53 record
  • ECR repo + ECS service + task role
  • A GitHub Actions pipeline to build and deploy

Stage 2 of 6~50k → 2M users

Many copies

Run the same service many times and put the page on a CDN, close to users.

Move here when: CPU sits above ~70% at peak, or one crashed instance takes the whole site down.

In junior terms

Horizontal scaling
More copies of the same server instead of one bigger server.
Stateless
The server remembers nothing between requests, so any copy can serve anyone.
Autoscaling
A robot that adds copies when they’re busy and removes them when it’s quiet.
CDN / edge cache
Copies of your files stored in cities near your users, so the page loads fast everywhere.
WAF
A bouncer at the door who blocks obvious bots and floods before they reach your code.
Availability Zone
Separate data-centre buildings in one region. If one floods, the others keep serving.

What actually changes

Code change: make the page cacheable. The ~35 pictures, scripts and styles are already separate files a CDN can cache. Only the HTML is different on each load, because it carries a fresh CSP nonce. Every script is already its own file, so the policy 'self' alone is enough; drop the nonce and the HTML can sit on the edge too.

Traffic math: 2M daily users ≈ 160 requests/s on average and ~500/s in the peak hour. Each API call does about 1 ms of work, so a handful of copies is enough. You’re buying resilience here more than raw speed.

On Render you…

  • Set instances to 2+ (never 1 in production)
  • Turn on autoscaling: min 2, max 10, CPU 70%
  • Serve the page as a cached static asset

On AWS you…

  • Launch template / ECS service across 3 AZs
  • Target-tracking scaling policy
  • CloudFront with 2 origins: S3 for /, ALB for /api/*
  • WAF managed rule groups + rate rules

Stage 3 of 6When features need to remember

Shared memory

Add a fast shared cache and a real database, reached over a private network.

Move here when: You want burn-after-reading scrolls, ‘my scrolls’ for signed-in users, abuse reports, or rate limits that hold across copies.

In junior terms

Redis / Key Value
A shared whiteboard in memory. Every copy reads and writes it in under a millisecond, and it’s fine if it’s wiped.
Postgres
The filing cabinet. Slower than the whiteboard, but it never forgets and never half-saves.
Connection pool
Shared phone lines to the database, so 50 servers don’t each dial 20 lines and jam it.
Multi-AZ / HA standby
A twin database in another building that takes over automatically if the first dies.
Private subnet
Machines with no public address. Only your own servers can reach them.
Secrets Manager
A safe for passwords, instead of pasting them into config files.

What actually changes

Code change: move the per-visitor tally in site_security/limit_requests_per_visitor.py from memory to Redis INCR + EXPIRE. It’s one small file, so nothing else changes.

Burn-after-reading needs one atomic step: UPDATE scrolls SET opened_at = now() WHERE id = $1 AND opened_at IS NULL. If no row changes, someone else already opened it.

Watch connections: 10 instances × 2 processes × 4 threads = 80 database connections. Pool them (PgBouncer on Render, RDS Proxy on AWS).

On Render you…

  • Create Postgres + Key Value in the same region
  • Reference their internal URLs in render.yaml env vars
  • Pick an HA-capable Postgres plan

On AWS you…

  • DB subnet group in private subnets
  • RDS Multi-AZ + RDS Proxy + parameter groups
  • ElastiCache cluster + security group rules
  • Secrets Manager + IAM so tasks can read the secrets

Stage 4 of 6When ‘complex processing’ arrives

Heavy lifting in the back

Slow work moves off the request path into a queue that background workers drain.

Move here when: New features take seconds, not milliseconds: illustrated scrolls (AI images), read-aloud audio, translation, moderation scans.

In junior terms

Queue
The ticket rail in a restaurant kitchen. The waiter pins an order and goes back to guests; cooks take tickets when they’re free.
Worker
A server with no website. It only takes tickets and cooks them.
202 Accepted
“Got it, working on it.” Not “done”.
Idempotent
Cooking the same ticket twice gives one dish, not two. Needed because retries happen.
Dead-letter queue
The pile of tickets that failed five times, set aside for a human to look at.
Object storage (S3)
A bottomless shared drive for files, each reachable by a URL.

What actually changes

Rule of thumb: anything slower than ~300 ms, or anything that calls a third party that might hang, goes to the queue.

Sizing: if 10% of 2M daily seals ask for an illustration at ~5 s each, that’s 1M worker-seconds a day, or about 12 workers busy around the clock (~60 at peak). That’s why they autoscale on queue depth.

Render has no GPUs and no object store. Call an AI API, or a GPU host, from the worker, and write files to S3 or Cloudflare R2.

On Render you…

  • Add a type: worker service to render.yaml
  • Use Key Value as the broker (RQ, Celery, Dramatiq)
  • Add a type: cron job to purge old files
  • Create an S3/R2 bucket; keys in env vars

On AWS you…

  • SQS queue + DLQ + redrive policy
  • Worker ECS service, scaling on ApproximateNumberOfMessagesVisible
  • S3 bucket behind CloudFront (Origin Access Control)
  • Bedrock access or a GPU instance group

Stage 5 of 6~5M+ users, several teams

Everyone wants to know

Publish every important fact once to an event log. Any number of systems read it independently.

Move here when: Analytics, moderation, notifications, search and ML all want to react to ‘spell cast’ or ‘scroll opened’, and you’re tired of editing the web app for each one.

In junior terms

Event
A fact that happened: “a healing spell was cast at 21:04.” Never a command.
Kafka topic
An append-only diary of events. Nobody tears out pages; everyone reads at their own pace.
Consumer group
One team reading the diary. Each team keeps its own bookmark.
Partition
The diary split into volumes so many readers can work in parallel. Events for the same scroll stay in order within one volume.
Outbox pattern
Save the data and a ‘please publish this’ note in the same database transaction, so you never save without announcing (or announce without saving).
Warehouse / data lake
Where you ask big questions, like “scrolls opened last month by country”, without slowing the live database.

What actually changes

Kafka is the most over-adopted piece on this page. Don’t add it just for scale. At 160 events/s, Postgres plus a queue is plenty. Add it when the number of different consumers grows, or when you need replay.

A cheaper first step on Render is Redis Streams in Key Value. It has the same consumer-group idea and fits modest volumes.

Key events by scroll_id so each scroll’s events stay in order. Keep them 7 days. Version the schemas.

On Render you…

  • Sign up for hosted Kafka (or start with Redis Streams)
  • One worker service per consumer group
  • Relay outbox rows to Kafka from a small worker

On AWS you…

  • MSK (provisioned or Serverless) in private subnets
  • IAM auth + topic ACLs
  • Glue Schema Registry
  • Firehose → S3 → Athena/Redshift

Stage 6 of 620M users, several continents

Planet scale

Run the whole stack in two or more regions, route each user to the nearest healthy one, and describe everything as code.

Move here when: Users in Europe and Asia see 200 ms+ latency, one region outage would take you down, EU data must stay in the EU, or many teams deploy every day.

In junior terms

Region
A cluster of data centres in one part of the world (Virginia, Ireland, Frankfurt…).
Latency routing
DNS that sends each person to the nearest region that’s currently healthy.
Replication lag
The other region’s copy of the database is about a second behind.
Failover
Promoting the copy to be the main database when the main region is down.
Infrastructure as Code
Your servers described in files (Terraform, CDK) that can be reviewed like code and recreated in minutes.
Observability
Logs (what happened), metrics (how much, how fast) and traces (the path one request took).
SLO
A promise you measure, like “99.9% of reveals answer in under 300 ms”.

What actually changes

Most apps with 20M users are not multi-region. Single region, multi-AZ, a CDN and good backups covers most needs. Go multi-region for latency-sensitive users on other continents, legal data residency, or an uptime promise that can’t tolerate a regional outage.

This is where Render stops being the easy answer. It can still run the stateless tiers well. The global data layer, compliance controls and per-hop tuning are where AWS (or GCP/Azure, or Kubernetes) earns its complexity.

On Render you…

  • Duplicate services in a second region from the same Blueprint
  • Put a global load balancer in front
  • Move data to a multi-region database, or accept cross-region writes

On AWS you…

  • Terraform/CDK modules per region
  • Aurora Global Database + tested failover
  • ElastiCache Global Datastore, MSK Replicator
  • Route 53 health checks + latency records

What I’d actually do

  1. Ship stage 1 on Render today. It costs nothing to learn from.
  2. Go to stages 2–4 on Render as features demand. They map cleanly onto its web, worker, cron, Postgres and Key Value services.
  3. Reconsider at stage 5–6, or when the bill, compliance or a missing product (GPUs, global data, Kafka) makes AWS’s assembly worth it. Stateless tiers move easily; plan the data move early.

Already in the code for scale

  2. /healthz, config from env, one Docker image for every environment.
  3. All security code in one place: site_security/.
  4. Per-visitor rate limit in one small file, ready for Redis.
  5. Next code changes: drop the nonce so the HTML can be cached (stage 2), Redis limiter (stage 3), 202 + job endpoints (stage 4), outbox table (stage 5).
